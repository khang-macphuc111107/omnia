# T1.7 — Set `TRUST_PROXY=true` for htmustc-proxy (operator action)

## Problem
The dashboard login lockout (`internal/api/session/limiter.go`) keys on the client
IP from `ClientIP(r)`. Behind the Caddy edge the request's `RemoteAddr` is Caddy's
own container IP, so **every** `/management` login shares one lockout bucket — five
failed logins from any single anonymous caller lock out **all** operators.

## Why no code change was needed
`ClientIP` already honours `TRUST_PROXY`: when it is `true`, it reads the real
client IP from `X-Forwarded-For`. And this is safe here because Caddy's
`must1c_realip` snippet (`infra/caddy/Caddyfile.docker`) strips any
client-supplied `X-Forwarded-For` and rewrites it to the real TCP peer:

```
(must1c_realip) {
	request_header -CF-Connecting-IP
	request_header -X-Real-IP
	request_header -True-Client-IP
	request_header -X-Forwarded-For
	request_header X-Forwarded-For {remote_host}
}
```

So the single XFF value the app sees is the genuine client IP and cannot be
spoofed. The only missing piece is turning the flag on for this container.

## The change to apply (operator)
Add `TRUST_PROXY: "true"` to the `htmustc-proxy` service `environment:` block in
`docker-compose.yml`:

```yaml
  htmustc-proxy:
    # ...
    environment:
      HTMUSTC_PUBLIC_BASE_URL: ${HTMUSTC_PUBLIC_BASE_URL:-}
      TRUST_PROXY: "true"        # <-- add: real client IP from Caddy's rewritten XFF
```

Then redeploy the htmustc-proxy container.

## Do NOT
Do not set `TRUST_PROXY=true` on any deployment whose edge does not strip inbound
`X-Forwarded-For` — there, a client could spoof XFF to evade its own lockout or to
lock out a victim IP. The Caddy config above is what makes it safe on this stack.
